- That migration surfaced a real gotcha, logged as `CONTRIBUTING.md` item 16: manually merging a subclass's `model_config` (`ConfigDict(**Parent.model_config, frozen=True)`) hits both `ruff`'s `RUF012` (dict-literal-via-unpacking reads as a mutable default) and a `pyright` overload conflict (it can't prove `frozen` isn't already in the unpacked `TypedDict`). **Why:** All three are reusable code/tooling facts, not step-specific context — future steps will keep writing round-trip tests (hitting the `flake8-aaa` naming quirk again) and keep adding wire models (hitting the `CamelModel` question again). ## Step B5 — 2026-09-13

**What changed:**
- Wrote the `429` integration test with `app.dependency_overrides[get_rate_limiter] = lambda: RateLimiter(per_minute=1)` and it failed — the second of two requests came back `200`, not `429`. Root cause: FastAPI calls an override lambda fresh on every dependency resolution, so `lambda: RateLimiter(...)` handed each request its own empty counter instead of one shared, accumulating instance. Fixed by binding a single instance first (`limiter = RateLimiter(per_minute=1); app.dependency_overrides[get_rate_limiter] = lambda: limiter`) — same fix applied to the always-permissive default override in `tests/conftest.py`, which had the identical latent bug (harmless there only because the limit was so high it never mattered). Logged as `CONTRIBUTING.md` item 23.
- `rest-api-tester`'s manual run of `POST /v1/draft` flagged that the `400` error `message` embedded a raw traceback fragment (file path, line, function name) — `_validation_exception_handler` had been built with `str(exc)` on the `RequestValidationError`, which formats like a traceback rather than a clean message. Fixed to build the message from `exc.errors()` instead. No unit test would ever have caught this (nothing asserts on exact error text), which is exactly the gap `rest-api-tester`'s manual/read-only verification exists to cover. Logged as item 24.
- Actually running `make start_dev` and hitting `POST /v1/draft` for real (not just against mocked models) surfaced that `get_agent()` was building `Agent("provider:model")` from a bare string — which makes PydanticAI construct its own provider client from that provider's *own* conventional env var (`OPENAI_API_KEY`), completely ignoring `Settings.llm.api_key`. Every existing unit/integration test bypasses `get_agent()` via dependency injection (`agent=Depends(get_agent)` overridden to a stub), so none of them could have caught this — it only surfaced because this step's manual dev-server check happened to try a real (if fake-keyed) request end-to-end. Fixed by building the `Provider` explicitly (`infer_provider_class(...)(api_key=...)`) and passing it via `infer_model`'s `provider_factory`. Logged as item 22.
- Also hit `ruff`'s B008 false-positive on `Depends(...)` defaults whenever the parameter's annotation is a subscripted generic (`Agent[None, X]`); fixed project-wide via `extend-immutable-calls` rather than per-callsite. Logged as item 21.
- `.env.example`'s mere existence (from B4) turned into an active test-isolation bug once `config__test.py`'s "field absent" tests were written against it: any developer who's run `make init` has a real `.env`, and `Settings()`'s `.env`-file source reads it independently of `monkeypatch.delenv`. Fixed with `Settings(_env_file=None)`. I hit this myself mid-step (forgot to remove a `.env` I'd created for manual testing) — worth stating plainly: this wasn't a hypothetical, it broke a real test run in this exact session. Logged as item 20.

**Why:** All five are reusable facts about this stack, and four of the five were only caught because this step did real manual verification (`make start_dev` + curl, `rest-api-tester` against a live server) rather than stopping at mocked-everything unit tests — the mocked tests are exactly what let a wrong-by-default agent construction and a leaky error handler ship undetected through two commits (B4, and this one's earlier draft) before anyone actually ran the thing. Recorded in `CONTRIBUTING.md` per `SELF_IMPROVE.md` step 3.

**Generalized to `PROCESS.md`:** none of this step's issues were about the loop itself (the loop already mandates `rest-api-tester` for new HTTP surface, and that's exactly what caught the traceback leak) — but the pattern across B4 and B5 ("a real request path can be silently wrong when every test mocks the one thing that matters") is now two data points, not one. Worth watching in B6 (which explicitly deals with the canonical-integrity check on real LLM output) for whether it recurs a third time and earns an actual process change.
